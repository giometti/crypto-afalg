# craf

`craf` seals a stream into a single-file archive encrypted with AES-256-CBC, and unseals it; it also decrypts the files of `openssl enc -pbkdf2` (below, *enc -d*) and computes the digests and checks the signatures of `openssl dgst` (below, *dgst*). The cipher runs in the kernel, through [libkcrypto](libkcrypto.md) and `AF_ALG`, with a key taken from the keyring by serial, or loaded from the blob of a trusted key that the archive carries: either way the key of seal and unseal does not pass through craf's memory (that of enc -d does, below). seal and unseal therefore need a kernel 6.2 or newer with `KEYS`, and a libkcrypto that takes keyring keys (see `kc_key_serial_supported()`; crypto-afalg shows `-S|--keyserial` in its help exactly when it does): without them every seal and unseal exits with status 3.

```bash
$ craf seal -cipher-driver cbc-aes-ce -enc-key @s,user,backup < data.tar > data.craf
$ craf unseal -enc-key @s,user,backup < data.craf > data.tar
$ craf seal -cipher-driver cbc-aes-ce -enc-blob key.blob < data.tar > data.craf
$ craf unseal < data.craf > data.tar
```

  * `-in <file>`, `-out <file>`: read and write files instead of stdin and stdout. `-out` is written as stdout would be: it is truncated once the options are checked and the input is open, and kept whatever the exit status, so an error found in the options, in the archive's header (a key option it does not take included) or in loading the key leaves it empty, and one found while decrypting leaves what was written before it: with a wrong padding every block but the last, with a wrong length every whole block (up to v1.3.0, every whole block but the last), as `openssl enc -d` does. The input and the output cannot be the same regular file, nor can the output be the `-enc-blob` file.
  * `-cipher-driver <driver>` (seal): the kernel driver of `cbc(aes)` to encrypt with, by its exact name (see `/proc/crypto`), at most 63 characters. The name of an algorithm, or a driver of another algorithm, is a wrong usage.
  * `-cipher-algo cbc(aes)` (seal): let craf choose the driver, the one of highest priority among the tested, not internal drivers of `cbc(aes)` in `/proc/crypto`, the first listed among equals: the rule of the kernel's own choice, as its sources state it (`__crypto_alg_lookup()`). Give either `-cipher-driver` or `-cipher-algo`. Some drivers that the kernel prefers cannot be used through `AF_ALG` (on i.MX, `cbc-aes-tee`): there, name the driver.
  * The driver that encrypted is written in the archive, and unseal uses the same one, only if `/proc/crypto` already lists it as a driver of the archive's algorithm: craf binds no driver an archive names before that check, so an archive cannot make the kernel build one. A driver the kernel builds from a template, such as `cbc(aes-generic)`, is listed only once something has used it since the boot. A driver the archive names and `/proc/crypto` does not list makes unseal exit with status 3; one it lists for another algorithm means the header is false, status 1. Either way, one of these takes the place of the archive's driver:
    * `-cipher-driver <driver>` (unseal): a driver named on the command line, checked as for seal;
    * `-any-driver` (unseal): the one `-cipher-algo` would choose.
  * `-enc-key <key>` (seal, and unseal of an archive sealed with it): the key, of 32 bytes, a serial number or `[<keyring>,]<type>,<description>` as for crypto-afalg `-S`. With two commas the first field is the keyring, so a description with a comma needs the keyring: `user,a,b` is the key of type `a` and description `b` in `@u`. A description that the kernel's search finds in more than one key is refused, among the keyrings craf can read, and a key there that craf cannot examine makes it exit with status 3 and "cannot tell whether the key <N> is also ..." (see crypto-afalg `-S` in the README for which keys); a serial number is not looked up, and needs neither. craf checks the length of a `user` key only; for any other type, such as `logon` or `trusted`, creating it with 32 bytes is up to you.
  * `-enc-blob <file>` (seal): the blob of a trusted key, in hex as `keyctl pipe` writes it (a final newline, as `keyctl print` writes it, is accepted), at most 65535 bytes. craf loads it into the keyring of its own thread, which no other process can search and which goes with the process, encrypts with that key, writes the blob into the archive and removes the key; unseal of that archive takes no key option, and loads the blob from the archive in the same way. The blob loads only where a trust source holds the key that sealed it (a TPM, a TEE such as OP-TEE, CAAM): what that means for the archives is below, with what they protect. It needs a kernel with trusted keys (`TRUSTED_KEYS`) that its `AF_ALG` can reach (trusted keys built in, or both as modules; otherwise setting the key fails with "Protocol not available"), and a trust source. A blob that needs options to load, such as a policy or a password, cannot be used. A trusted key is of 32 to 128 bytes and AES takes 32 at most, so make it of 32 (`keyctl add trusted <name> "new 32" ...`): a longer one makes seal exit with status 3. Give either `-enc-key` or `-enc-blob`, and write options in full: an abbreviation such as `-enc` names more than one.

The exit status is:

  * 0 when the work is done;
  * 1 when the archive is refused: its format (also a driver it names that `/proc/crypto` lists for another algorithm), a truncation, `bad decrypt`;
  * 2 for a wrong usage, also a `-cipher-driver` that is not a driver of `cbc(aes)`, a malformed or ambiguous `-enc-key`, a `user` key that is not of 32 bytes, `-enc-key` and `-enc-blob` together or neither for seal, `-enc-key` missing for an archive sealed with it or given for one that carries its key, an `-enc-blob` file that is empty, not a blob in hex or longer than 65535 bytes, or a `-out` that is the `-enc-blob` file;
  * 3 when craf could not do it: a driver or a key that is not there, an `-enc-key` whose uniqueness could not be checked, a driver in the archive that `/proc/crypto` does not list, an archive of a newer version or with a key source this craf does not know (it may be good: a newer craf can read it), `/proc/crypto` unreadable, an input or output error, an `-enc-blob` file that cannot be read, a blob the kernel does not load (an archive of another system, a blob that was changed, a kernel without trusted keys or without a trust source up, a blob that needs options to load), a trusted key that `AF_ALG` cannot use (trusted keys it cannot reach, a key longer than 32 bytes).

**The output is valid only with exit status 0**: unseal writes the data as it decrypts them and checks the padding at the end, so whatever it wrote before a refusal must be discarded. In a pipe, craf sees only the end of its input: a script checks the status of every command of the pipe (`set -o pipefail`), for example of the `tar` that feeds seal.

The archives of this version are encrypted, not authenticated. craf refuses a header it does not understand, an archive cut to a length that is not one of an archive, and almost always a wrong key or an archive cut by whole blocks, through the padding. The data stay secret from whoever does not have the key only as long as nobody can make unseal run on archives they have changed and see how it ends: the padding check then tells, archive after archive, something of the content. Without the key, a change to the encrypted data or to the IV goes undetected, decrypts to data changed where the change chose (a change to the IV alters the first block exactly, nothing else) with exit status 0, unless it reaches the padding; so unseal should not run on its own on archives from media that others can write. craf does not detect the replay of an older archive sealed with the same key, and it cannot protect against somebody who can use the key, for example root on the running system. An archive sealed with `-enc-blob` carries its key as a blob that any program on the system can have the trust source load, with no privilege and without craf: there, whoever can read the archive can decrypt it, and whoever can load a blob can make an archive of their own content that unseal takes with exit status 0; on that system only the read permissions of the archives and of the blob file protect them, not those of craf. Such an archive opens only where a trust source holds the key that sealed its blob: with a trust source that has a key of its own (a provisioned TPM, an OP-TEE with a hardware unique key, a closed CAAM) that is this system only, and no longer once that state changes (a TPM cleared or its parent key removed, an update of the trust source that changes how it derives its keys), so keep the archives you may need openable across such changes, or seal them again before; with one in a development state (an OP-TEE with the default unique key, a CAAM not closed) it is every system of that kind. Authentication will come with version 2 of the format, and craf will still unseal the archives of version 1.

The archive format, version 1, integers little-endian, a string being its length in one byte, 1 to 255, followed by as many characters from 0x21 to 0x7e (printable ASCII without the space):

| field | size | value |
|---|---|---|
| `magic` | 8 | `AFALGARC` |
| `version` | 2 | 1 |
| `hdr_len` | 2 | the length of the whole header |
| `cipher_driver` | string | the driver that encrypted |
| `cipher_algo` | string | `cbc(aes)` |
| `key_len` | 1 | 32 |
| `key_source` | string | `serial`: the key is the caller's; `trusted`: the key is the blob that follows |
| `iv` | 16 | random |
| fields of the key source | | none for `serial`; for `trusted`, `blob`: its length in 2 bytes, at least 1 (the header ends with it, so at most 65535 less the rest of the header), then the bytes of the blob as the kernel gives it (`keyctl pipe`, decoded from hex) |
| data, from `hdr_len` | n x 16 | AES-256-CBC of the input with PKCS#7 padding |

The first 12 bytes, `magic`, `version` and `hdr_len`, keep their place in every version, so that a reader tells an archive of another version from something else.

The tests of seal and unseal need `keyctl`, `openssl` and `cbc(aes)` in the kernel; without them they are `Skipped`. They use the driver `-cipher-algo` chooses, or the one `CRAF_TEST_DRIVER` names, for a kernel whose preferred driver cannot be used through `AF_ALG`. The test that seals with a trusted key (`[trusted]`) creates one with the options of `new` in `CRAF_TEST_TRUSTED` (on a TPM 2.0 the parent key, for example `keyhandle=0x81000001`): without the variable it is `Skipped`, with the reason, where the key cannot be created; with it, a key that cannot be created is a failure. libkcrypto's test of trusted key blobs (`[blob-trusted]`) takes the same variable, in the same way.

## enc -d: the files of openssl enc

`craf enc -d` decrypts a file that `openssl enc -pbkdf2` wrote, with the cipher in the kernel: the same command line, the name of the command apart, opens the same files.

```bash
$ craf enc -d -in rootfs.tar.xz.enc -aes-256-cbc -pbkdf2 -kfile rootfs.key | tar xJf -
$ craf enc -d -cipher-driver cbc-aes-ce -cipher-algo 'cbc(aes)' -cipher-key-len 32 -pbkdf2 -kfile rootfs.key < in.enc > out
```

  * `-d` is required: craf does not encrypt (`-e` given last is refused, as openssl would encrypt).
  * The cipher, by the name openssl gives it, as an option: `-aes-256-cbc`. craf translates it into the name of the kernel, `<alg>-<bits>-<mode>` into `<mode>(<alg>)` with a key of `<bits>/8` bytes, `<alg>-<mode>` into `<mode>(<alg>)` with the only key length the kernel takes, and `des-ede3-cbc`, which the kernel calls `cbc(des3_ede)`, from a table; it prints the translation as a warning, and the kernel decides whether it has that cipher (exit status 3 if not). A name in neither form, such as openssl's aliases `-aes256` or `-des3`, or one in capitals, is an unknown option (exit status 2): give the full name. Or by the name of the kernel's algorithm, `-cipher-algo <name>` (a driver goes in `-cipher-driver`: given here, it is a wrong usage), with `-cipher-key-len <bytes>` (1 to 64) where the kernel takes more than one length, and no warning; an openssl name for such a cipher, as `-cast5-cbc`, does not say the length, so craf asks for this form. Not both. A name of the kernel is at most 63 characters long. A word that begins as an option of craf (`-cipher-`, `-in`, `-out`, `-pass`, `-kfile`, `-iter`, `-md`, `-pbkdf2`) is never taken for a cipher.
  * The modes the format of `openssl enc` has no room for, which openssl refuses too, are a wrong usage: AEAD (`gcm`, `ccm`, `ocb`, `siv`, `poly1305`, and the kernel's `rfc4106`, `rfc4309`, `rfc4543`, `rfc7539`, `rfc7539esp`), `xts` and key wrap (`wrap`, the kernel's `kw`); another AEAD of the kernel, such as `authenc(...)`, is no skcipher and exits with status 3, not available. craf decrypts CBC only for now: another mode the kernel has, such as `ecb`, `ctr` or `cts(cbc(aes))`, exits with status 3, "craf does not decrypt ... yet".
  * `-pbkdf2`, or `-iter <n>` (1 or more, in decimal, or in octal or hex as openssl reads it: `010000` is 4096; 10000 when not given), and `-md <hash>` (`sha256` when not given, at most 57 characters), passed to the kernel as `hmac(<hash>)`: a hash the kernel does not have exits with status 3, and so does one openssl and the kernel name differently, such as openssl's `blake2b512`. `<hash>` can be a driver of the hash too, such as `sha256-ce`, where the one the kernel prefers cannot be used through `AF_ALG`. The derivation of openssl without `-pbkdf2`, which openssl itself calls deprecated, is not supported.
  * The passphrase, as openssl takes it: the last of `-k` and `-kfile`, which win over `-pass` whatever the order, or else the last `-pass`. `-kfile <file>`, its first line, of which openssl takes at most 127 characters and strips up to two `\n` or `\r` at the end; `-pass file:<file>` and `-pass fd:<n>`, the first line up to its `\n` (a `\r` stays in the passphrase), at most 1023 characters; `-pass env:<name>`; `-pass pass:<text>` and `-k <text>`. Where openssl cuts a passphrase, craf cuts it the same way and says so in a warning. An empty `-kfile`, or one whose first line is empty, an empty `file:` or `fd:`, a missing variable of `env:`, a `fd:` that is the input, and a source other than `pass:`, `file:`, `env:` and `fd:` (`-pass stdin` too) are a wrong usage; an empty passphrase given otherwise is taken, as openssl takes it. A descriptor of `fd:` that is not open exits with status 3, before craf opens a file of its own. craf never asks for a passphrase.
  * **`-k` puts the passphrase on the command line**, where other processes read it (`/proc/<pid>/cmdline`), and **`-pass env:` leaves it in the environment of the process** (`/proc/<pid>/environ`, for its user and root), which craf cannot clear: they are there for compatibility; use `-kfile`, `-pass file:` or `-pass fd:`. A passphrase read from a file stays in craf's memory only until the key is derived.
  * `-salt`, the default when decrypting, is taken with a warning that it has no effect. The other options of `openssl enc` (`-a`, `-base64`, `-nosalt`, `-K`, `-iv`, `-S`, `-nopad`, `-p`, `-P`, `-v`, `-bufsize`, `-none`, `-z`) are a wrong usage, and so is any other option, as an unknown one.
  * `-in`, `-out` and `-cipher-driver` as for seal and unseal; the output cannot be the file of the passphrase either (`-kfile`, `-pass file:`, or the file of `-pass fd:`), since it is truncated before the passphrase is read. With `-cipher-driver` craf binds that driver only, never the name of the algorithm, so a driver the kernel prefers and that cannot be used through `AF_ALG` is never touched.
  * craf reads the sizes of the cipher, and checks a driver, in `/proc/crypto`: `/proc` must be mounted (exit status 3 otherwise), which `openssl enc -d` does not need.

The exit status is that of seal and unseal: 1 when the file is refused, a header shorter than 16 bytes or without `Salted__`, a length that is not one of whole blocks, a wrong padding; 2 for a wrong usage; 3 when craf could not do it. What craf wrote before a refusal is what `openssl enc -d` writes: nothing for a refused header, every whole block for a wrong length, every block but the last for a wrong padding; as for unseal, **the output is valid only with exit status 0**: in a pipe, unless craf is its last command, a script sees it with `set -o pipefail` or with bash's `PIPESTATUS`. A wrong passphrase is seen through the padding only, as with openssl: about once in 256 tries it gives exit status 0 and garbage, and the format of `openssl enc` has no room for an authentication.

The tests of `enc` use `openssl enc` as the oracle; without it, with an openssl without `-pbkdf2` (before 1.1.1), or without `cbc(aes)` in the kernel, they are `Skipped`.

## dgst: the digests of openssl dgst

`craf dgst` computes a digest, and checks a signature, as `openssl dgst` does, with the hash and the check in the kernel: the same command line, the name of the command apart, prints the same, but where said below.

```bash
$ craf dgst -sha256 rootfs.tar.xz
SHA2-256(rootfs.tar.xz)= 5b2f...
$ craf dgst -digest-algo sha256 -binary < rootfs.tar.xz > rootfs.sha256
$ craf dgst -sha256 -verify rootfs.sign.key -signature rootfs.sig rootfs.tar.xz
Verified OK
```

  * The hash, by the name openssl gives it, as an option: `-sha256`, `-sha384`, `-sha3-256`, ... The name goes to the kernel as it is: sha1, sha2 and sha3 have the same names in openssl and in the kernel, and a table for the names that differ, empty for now, is the place where a translation would go, printed as a warning. The name of a driver, such as `-sha256-generic`, is a wrong usage, as for `-digest-algo` and for openssl. A hash the kernel does not have, also by that name, exits with status 3: so do openssl's `blake2b512` (the kernel's `blake2b-512`) and `ripemd160` (`rmd160`). Without a hash, `sha256`, as openssl.
  * `-digest-algo <hash>`: the hash by the name of the kernel, at most 63 characters, no white space nor `=`, without a warning; not together with a hash option. The name of a driver, such as `sha256-generic`, is a wrong usage: craf names the algorithm it is a driver of. Which hashes there are, the kernel says; that a name is a driver, `/proc/crypto` (for a hash option too), so without it craf exits with status 3.
  * The output is that of openssl: `<label>(<file>)= <digest in hex>`, one line per file, `(stdin)` when there is no file. The label is what OpenSSL 3 prints: `SHA2-256` for `-sha256`, and `SHA1`, `SHA2-224` to `SHA2-512`, `SHA3-224` to `SHA3-512`, `MD5` and `SM3` for the others it names its own way; `SHA256` without a hash option (OpenSSL 3.0.13 prints the default hash so); the name of the kernel for any other hash and with `-digest-algo`. `-binary` writes the bytes of the digest instead, `-hex` the line; the last of the two given wins.
  * A file that cannot be read is told on stderr and the others are still computed; the exit status is then 3. A hash the kernel cannot open stops at once.
  * `-keyform PEM` or `-keyform DER`, in any case, as openssl takes it: craf tells the format of a key file by itself, and uses the option for nothing; without `-verify` it has no effect, as a warning says. Another value is a wrong usage.
  * The other options of `openssl dgst` that craf knows of and does not implement are a wrong usage, said so: `-sign`, `-prverify`, `-sigopt`, `-out`, `-r`, `-c`, `-hmac`, `-mac`, `-macopt`, `-xoflen`, `-list`, `-d`, `-debug`, `-passin`, `-engine`, `-engine_impl`, `-provider`, `-provider-path`, `-propquery`, `-rand`, `-writerand`, `-fips-fingerprint`; so is any other option, as an unknown one, and an abbreviation of one, also when it could name more than one.

  * `-verify <file> -signature <file>`: the signature, by RSA PKCS#1 v1.5 (`openssl dgst -sign`), of the one file given, or of stdin, checked with the public key in the first file. The kernel checks it (`KEYCTL_PKEY_VERIFY`): craf computes the digest, with the hash of the command line, and hands the kernel the digest, the signature and the key, as a key of the keyring of its own thread, out of reach of any other process and taken out at the end.
    * The key, as `openssl dgst -verify` takes it, PEM or DER: a public key (`PUBLIC KEY`, as `openssl pkey -pubout` writes it) or an RSA public key of PKCS#1 (`RSA PUBLIC KEY`); also a certificate (`CERTIFICATE`), which openssl does not take, whose key is used. In DER, the bytes after the key are left out, as openssl leaves them; a key file is of at most 64 KiB, an RSA key of at most 16384 bytes. The kernel takes a key only within a certificate, so craf wraps a public key in one that names no real issuer and whose signature is none; the kernel checks the signature of a self-signed certificate only, and refuses one whose signature does not hold. craf does not check a certificate: the trust is in the file of the key, as with openssl.
    * An RSA key only; another key, or a file that is none of these, exits with status 3. `-keyform` is not needed: one that does not match the file is said in a warning, and the file is read as what it is.
    * As openssl, a signature file is read for at most the length of the key's signatures, so a longer file is checked by its first bytes; an empty one is refused.
    * craf asks the kernel first whether it can use the key with these parameters (`enc=pkcs1 hash=<hash>`), so that a hash or a key the kernel cannot use exits with status 3, not as a forged signature, and before the data are read.
    * The verdict goes to stdout, `Verified OK` or `Verification failure`, the cause of a failure to stderr; there is one with exit status 0 and 1 only, none with 2 and 3. `-hex` and `-binary` are taken, with a warning that they have no effect.
    * A signature with a weak hash (`-md5`, `-sha1`) or a key of fewer than 2048 bits is checked as openssl checks it, with a warning for each: which hashes and keys to trust is the verifier's choice, by the options it gives.
    * Only one file can be verified, as with openssl; `-signature` without `-verify` or `-verify-key`, and either without `-signature`, are a wrong usage.
    * The verdict is on the bytes craf read: a caller that reads the file again, to install it, gets what the medium gives that time, which a medium out of its control can make other bytes. Verify a copy where nobody else writes, a tmpfs for instance, and use that copy.
  * `-verify-key <key> -signature <file>`: the same check, with an asymmetric key that is already in the keyring, where openssl has no such option: a serial number, or `[<keyring>,]<type>,<description>` as for `-enc-key`, such as `@u,asymmetric,id:<subject key identifier>`. A type other than `asymmetric` written there is a wrong usage, and `-keyform`, for a key that is no file, has no effect, as a warning says; a key given by serial that is not asymmetric, or not RSA, exits with status 3, as the kernel reports it; a spec that names more than one key is refused as for `-enc-key`. Give either `-verify` or `-verify-key`.
    * **The trust is that of the keyring the key is taken from**: whoever can add a key to `@u` or `@s`, that user or root, can put there a certificate of a key of their own with the subject key identifier you name, since the kernel does not check the signature of a certificate that is not self-signed; and a spec that names the key by its description or identifier takes the one the kernel's search finds. Verify with a key taken from a keyring only nobody else can write, or by its serial when you loaded it yourself; a key compiled into the kernel (`.builtin_trusted_keys`) cannot be used from user space at all.

The exit status is 0 when every digest is computed, or the signature is verified; 1 when the signature is refused: data, signature or key that do not match, a signature of another hash, an empty signature file; 2 for a wrong usage; 3 when craf could not do it (a hash the kernel does not have, a file that cannot be read, a key that is not RSA or cannot be loaded, a key of the keyring that is not there, or given by serial and not asymmetric, a kernel without asymmetric keys, an output that cannot be written). openssl exits with 1 in all these cases: a script that looks only at zero or not zero sees no difference. Errors and warnings go to stderr, the digests and the verdict to stdout.

The tests of `dgst` use `openssl dgst` as the oracle; without it, without `sha256` in the kernel, or, for `-verify` and `-verify-key`, without `keyctl` or without asymmetric keys and X.509 certificates in the kernel, they are `Skipped`; both ask the kernel with a certificate in a session keyring of their own, where the test of `-verify-key` also puts its keys.

## Known bugs

  * Until the archives are authenticated, a wrong key can, rarely (about once in 256 tries), give exit status 0 and garbage as output, since the padding is the only check it can fail. The same holds, for good, for a wrong passphrase of `enc -d`: the files of `openssl enc` are not authenticated.
